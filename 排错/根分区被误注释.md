# 根分区被误注释：启动后多个服务失败

### 问题记录：根分区被误注释，重启后多个服务失败（已修复）

记录日期：2026-10-09。故障主机：`master`（`192.168.194.141`），系统为 RHEL 9.8，根文件系统为 XFS。用户完成下述恢复后，已通过 SSH 只读复查确认结果。

#### 1. 故障现象

在安装依赖、配置内核模块后的重启中，系统没有正常进入图形登录界面，屏幕提示：

```text
[FAILED] Failed to start Security Auditing Service.
[FAILED] Failed to start Crash recovery kernel arming.
```

当时 SSH 连接也被关闭，无法远程读取日志。故障虽然出现在这次重启后，但最后确认的原因是 `/etc/fstab` 中根分区记录被误注释。

![开机时 auditd 和 kdump 启动失败](<https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/01-boot-service-failures.png>)

进入文字控制台后，执行：

```bash
systemctl --failed --no-pager
```

当时共有 7 个失败单元，包括 `auditd.service`、`dbus-broker.service`、`dbus.socket`、`kdump.service`、`avahi-daemon.service`、`sysstat.service` 和 `vgauthd.service`。

![文字控制台中的失败服务列表](<https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/03-failed-services.png>)

#### 2. 临时进入文字模式，取得日志

如果图形界面无法进入，可以在 GRUB 菜单中选中第一项当前内核，按 `e`，找到以 `linux` 或 `linuxefi` 开头的长行，在整行末尾加一个空格并追加：

```text
systemd.unit=multi-user.target
```

删除该行中的 `rhgb quiet` 两个参数可以显示启动日志，其余参数保留。按 `Ctrl + X` 启动。本次编辑只影响当前这次启动；进入文字模式后仍需修复实际故障。

![GRUB 启动菜单](<https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/02-grub-boot-menu.png>)

在 root 控制台执行：

```bash
journalctl -b -u auditd -u kdump --no-pager -n 80
```

关键日志如下：

```text
Couldn't open log file /var/log/audit/audit.log (Read-only file system)
mktemp: failed to create directory via template '/tmp/lsinitrd.XXXXXX': Read-only file system
chmod: changing permissions of '/var/lib/kdump': Read-only file system
```

这些错误表明，多个服务共同受到文件系统不可写的影响：审计服务写不了日志，kdump 创建不了临时文件，其他需要写入系统目录的服务也会失败。

![auditd 和 kdump 日志中的 Read-only file system](<https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/04-readonly-errors.png>)

#### 3. 根因：关闭 Swap 时，误注释了根分区

执行只读检查：

```bash
findmnt -no TARGET,SOURCE,FSTYPE,OPTIONS /
cat -n /etc/fstab
```

当时根分区显示为只读：

```text
/  /dev/mapper/rhel-root  xfs  ro,relatime,seclabel,...
```

`ro` 表示只读；`rw` 表示可读写。

截图中的 `/etc/fstab` 第 12 行把根分区 `/` 注释掉了，第 15 行的 Swap 记录却仍启用：

```fstab
# 错误示例：根分区被注释，Swap 仍启用
# /dev/mapper/rhel-root   /      xfs   defaults   0 0
/dev/mapper/rhel-swap     none   swap  defaults   0 0
```

根文件系统在启动早期可以先以只读方式挂载，再由系统按挂载配置切换为正常读写状态。这次根分区记录被注释后，没有按预期完成读写挂载，导致根分区保持 `ro`，进而出现多个服务启动失败。

![根分区为 ro，fstab 中根分区行被误注释](<https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/05-fstab-root-commented.png>)

辅助检查命令：

```bash
journalctl -b -u systemd-remount-fs.service --no-pager -n 40
journalctl -k -b -p err --no-pager -n 30
```

第一条当时返回 `No entries`，不能据此判断根分区正常；仍需结合实际挂载状态和 `/etc/fstab` 内容。第二条截取到的主要是驱动弃用和 VMware SMBus 提示；本次修复依据是明确的 `ro` 状态和被注释的根分区记录。



![当时截取的内核错误日志](<https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/07-kernel-warnings.png>)

#### 4. 恢复步骤

以下是本次故障的恢复流程，适用于已经确认根分区记录被误注释的情况。在虚拟机 root 控制台执行；普通用户需要先通过 `sudo -i` 进入 root。

**第一步：把根分区临时恢复为可写。**

```bash
mount -o remount,rw /
findmnt -no SOURCE,FSTYPE,OPTIONS /
```

检查输出是否包含 `rw`。如果重新挂载报错，先保留报错并继续诊断，不直接进行下面的写入操作。

**第二步：备份并修正 fstab。**

```bash
cp -an /etc/fstab /etc/fstab.before-root-fix
vim /etc/fstab
```

只修改两处：删除根分区记录前面的 `#`；在 Swap 记录前面加上 `#`。两条记录应分别为：

```fstab
/dev/mapper/rhel-root    /      xfs   defaults   0 0
# /dev/mapper/rhel-swap  none   swap  defaults   0 0
```

**以上仅展示要修改的两条记录，不是整个 fstab 文件。`/boot`、`/boot/efi` 和其他已有记录保持原样。**

在 Vim 中按 `Esc`，输入 `:wq`，再按回车保存并退出。

**第三步：验证挂载配置。**

```bash
findmnt --verify --verbose
```

确认没有解析错误或挂载配置错误后，继续执行：

```bash
systemctl daemon-reload
swapoff -a
reboot
```

重启时正常选择 GRUB 第一项即可，不需要再次添加临时文字模式参数。

#### 6. Vim 退出时遇到的小问题

当时把“不保存退出”的 `:q!` 输成了 `:!q`。Vim 将 `q` 当成外部 shell 命令执行，因此出现：

```text
/bin/bash: line 1: q: command not found
shell returned 127
Press ENTER or type command to continue
```

处理方法：先按回车关闭提示，再按 `Esc`，然后按需要输入：

| 命令 | 含义 |
| --- | --- |
| `:wq` + 回车 | 保存修改并退出 |
| `:q!` + 回车 | 放弃未保存修改并退出 |
| `:!q` | 执行名为 `q` 的外部命令，不是退出 Vim |

![Vim 把 :!q 当作外部命令执行](<https://raw.githubusercontent.com/XVSHIFU/Picture-bed/img/08-vim-wrong-exit-command.png>)

#### 7. 本次经验

- 关闭 Swap 时，按设备名称和文件系统类型定位：目标是 `/dev/mapper/rhel-swap`、类型 `swap`，而不是根分区 `/dev/mapper/rhel-root`、挂载点 `/`。
- 编辑 `/etc/fstab` 前先备份，修改后执行 `findmnt --verify --verbose`，再考虑重启。
- 多个服务同时失败时，先从日志中找共同错误。本次共同错误是 `Read-only file system`，应先解决挂载问题。
- `ro` 是只读，`rw` 是可读写；服务恢复情况用 `systemctl --failed --no-pager` 复查。
